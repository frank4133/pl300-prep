Exam overview & strategy

PL-300 validates your ability to prepare, model, visualize, and analyze data with Microsoft Power BI, and to deploy and maintain those assets.

1. Prepare the data (25–30%)

Getting data & storage modes

  • Import: data is cached in the model; fastest queries, full feature set; needs scheduled refresh. The default, and the usual “best performance” answer.
  • DirectQuery: nothing cached; every query hits the source. Use for near-real-time data or very large volumes; visuals are slower and DAX/PQ features are limited.
  • Dual: acts as cached or not depending on the query; typical for dimension tables joining a DirectQuery fact table plus Import aggregations (composite models) — reduces limited relationships and improves performance.
  • Live Connection: connects to Analysis Services or a published Power BI semantic model. To reuse an existing model and its measures with the least development effort, choose the Power BI semantic model connector.
Refresh requirementRecommended storage mode
Near real timeDirectQuery
Daily/weekly refresh, fastest visualsImport (or Import aggregations)
Dimension tables joined to a DirectQuery factDual

Power Query transforms that get tested

  • Merge = horizontal JOIN (add columns via a key); Append = vertical UNION (add rows). “One row per customer with city added” → Merge. “Two identically shaped tables into one” → Append Queries as New, then disable load on the originals to keep the model small.
  • Group By: aggregations (sum, count, min/max).
  • Pivot / Unpivot: Unpivot turns attribute columns into attribute/value pairs (wide → long); Pivot is the reverse. When column headers are data values (years, months), the answer is almost always Unpivot.
  • Transpose: swaps rows and columns wholesale — different from Pivot/Unpivot.
  • Use first row as headers, Fill Down/Up: fixes nulls caused by merged cells.
  • Split Column, Column From Examples: generate transforms from sample values.
  • Type errors like Expression.Error: cannot convert usually mean non-numeric characters in a column, or a renamed source column (column wasn't found → the source column was renamed).

Data profiling

  • Column quality: Valid / Error / Empty percentages.
  • Column distribution: Distinct vs Unique counts — tells you whether a column can be a key.
  • Column profile: statistics (min, max, average) and value distribution. Profiling covers the first 1,000 rows by default; switch to the entire data set if needed.

Query folding & performance

  • Query folding: steps translate back into the source’s native query (SQL). Check with “View Native Query” — grayed out means folding broke. Incremental refresh requires a folding-capable source.
  • Reference vs Duplicate: Reference reuses the original query’s result, so upstream changes flow downstream.
  • Shrink the model: remove unused columns/rows, disable auto date/time, avoid high-cardinality columns (GUIDs), pre-aggregate.

2. Model the data (25–30%)

Star schema & relationships

  • Fact tables hold transactions/measures; dimension tables hold descriptive attributes. Dimensions relate one-to-many into facts; cross-filter direction defaults to single (dimension → fact).
  • Cardinality: one-to-many is the norm. Avoid many-to-many; resolve it with a bridge table.
  • Bidirectional filtering adds ambiguity and cost — use only when required (bridge tables). To let RLS flow across a bidirectional relationship, tick “Apply security filter in both directions.”
  • Inactive relationships (dashed lines) are activated per-measure with USERELATIONSHIP() — the classic order-date/ship-date role-playing dimension setup.
  • Date table: “Mark as date table” is required for time intelligence on a custom date table; it needs one row per day, contiguous, no gaps.

Calculated columns vs measures vs calculated tables

Calculated columnMeasure
EvaluatedAt refresh, row by row, then storedAt query time, against the current filters
ContextRow contextFilter context
Model sizeConsumes memoryOnly the formula is stored

Core DAX concepts

  • CALCULATE(expression, filters…) rewrites filter context; combine with FILTER, ALL, ALLSELECTED, KEEPFILTERS, REMOVEFILTERS.
  • Iterators (X functions): SUMX / AVERAGEX / COUNTX / MAXX evaluate row by row then aggregate, e.g. SUMX(Sales, Sales[Qty]*Sales[Price]).
  • Time intelligence: TOTALYTD / DATESYTD (year to date), SAMEPERIODLASTYEAR / DATEADD(dates,-1,YEAR) (prior year), DATESINPERIOD (rolling windows, e.g. last 12 months), PREVIOUSMONTH.
  • Counting: COUNT (numeric), COUNTA (non-blank), COUNTROWS (rows), DISTINCTCOUNT (unique values).
  • Following relationships: RELATED (many side pulls from one side), RELATEDTABLE (one side pulls the many side), LOOKUPVALUE (no relationship needed).
  • Also tested: DIVIDE(a,b,alt) for safe division, SELECTEDVALUE, HASONEVALUE, ISFILTERED, CALCULATETABLE, SUMMARIZE, ADDCOLUMNS, CROSSFILTER, TREATAS.
  • VAR … RETURN improves readability and performance (repeated expressions evaluate once).
Sales YTD = TOTALYTD ( [Sales Amount], 'Date'[Date] )
Sales LY  = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
Rolling12 = CALCULATE ( [Sales Amount],
              DATESINPERIOD ( 'Date'[Date], MAX ( 'Date'[Date] ), -12, MONTH ) )

Row-level security (RLS)

  • Desktop: Modeling → Manage roles; define table-filter DAX such as [Region] = "West" or dynamic [Email] = USERPRINCIPALNAME().
  • Test in Desktop with “View as”; in the service, assign users/groups to roles on the semantic model’s Security page.
  • RLS applies only to Viewer-role users; workspace Admins, Members, and Contributors bypass it.

Performance tuning

  • Performance Analyzer (Desktop): records per-visual DAX timings; export to JSON.
  • Best Practice / VertiPaq analysis, DAX Studio: find memory-hungry columns.
  • Reduce cardinality (drop seconds, split datetime), use integer keys, prefer measures over calculated columns, add aggregation tables.
  • Large dataset storage format: enable on Premium when a model outgrows the default limit.

Interactions, filters & navigation

  • Filter scopes: visual → page → all pages (report). Slicers can be synced across pages via Sync slicers.
  • Edit interactions: choose whether a visual filters, highlights, or ignores the others.
  • Drill through: right-click a summary to jump to a detail page carrying the filter; the target page declares drill-through fields; add a back button.
  • Bookmarks + buttons + Selection pane: navigation, reset-filters, and show/hide toggles.
  • Tooltip pages: a report page used as a custom hover tooltip.
  • Conditional formatting: background/font color by measure, data bars, icons; “Field value” accepts a color-code column.
  • Top N filter: visual-level filter by measure.
  • Groups / bins: bucket continuous values or group categories.
  • Analytics pane: average/median/percentile lines, trend lines, error bars; line-chart Forecast and Anomaly detection.
  • Mobile layout: a separate portrait arrangement for phones.

Dashboards vs reports

  • Dashboards exist only in the service and are built by pinning tiles from reports. Data alerts work only on cards, KPIs, and gauges.
  • Alerts can trigger a Power Automate flow to email other people (built-in alerts notify only you).
  • Live tile cache time shows on the tile; report themes and dashboard themes are configured separately.
  • Subscriptions email report/dashboard snapshots on a schedule; comments support @mentions, including external users.

4. Manage and secure Power BI (15–20%)

Workspace roles (heavily tested!)

RoleKey rights
AdminEverything, plus delete the workspace, manage all members (including other admins), update/delete the app
MemberPublish/unpublish and update the app, add lower-privileged members, share content (“can invite others with least privilege” → Member)
ContributorCreate/edit/delete workspace content, schedule refresh; cannot share or publish the app (unless an admin delegates “update app”)
ViewerView and interact only; the only role RLS applies to
  • Notify a group about workspace issues: add it to the workspace contact list — no role needed (least privilege).
  • Apps: the recommended way to distribute content to many viewers; support audiences, optional Build permission on underlying models, and Teams installation.

Sharing & permissions

  • Semantic-model permissions: Read (view), Build (create reports on it / connect for analysis; required by Analyze in Excel), Reshare, Write.
  • “Build their own reports on an existing model” → grant Build; no workspace role required.
  • Endorsement: Promoted (any owner) vs Certified (authorized certifiers appointed by the tenant admin) — “financial-decision data must be reviewed and approved” → Certified.
  • Sensitivity labels (Microsoft Purview Information Protection): encrypt exported files (PDF/Excel/PPT) and prevent PII export; requires Azure Information Protection licensing.
  • Lineage view: trace source → semantic model → report → dashboard dependencies and upstream impact.

Refresh & gateways

  • On-premises sources (file servers, SQL Server, intranet) need an on-premises data gateway (standard mode is shared, multi-source; personal mode is single-user).
  • Cloud sources (OneDrive, SharePoint Online, Azure SQL) need no gateway; OneDrive/SharePoint files sync roughly hourly.
  • Scheduled refresh: up to 8/day on shared capacity, 48/day on Premium. After ~2 months of inactivity refresh is disabled for inactivity; anyone opening a dependent dashboard/report resumes it.
  • Incremental refresh: filters on RangeStart/RangeEnd parameters and refreshes only the newest partitions; requires query folding.
  • Refresh-failure notifications can go to the owner plus designated contacts in the semantic-model settings.

Deployment & governance

  • Deployment pipelines: Development → Test → Production; stage comparison and deployment rules (swap data sources/parameters per stage); needs Premium/PPU/Fabric capacity.
  • .pbit templates keep the model/queries/report definition without data, and can prompt for parameters — “share with colleagues for reuse without leaking data” → .pbit.
  • .pbip / Power BI Desktop developer mode: project format suited to version control.
  • Usage metrics report: views and viewers per report/dashboard.
  • Analyze in Excel: PivotTables over a semantic model; in Excel, Get Data → Power BI semantic model.
