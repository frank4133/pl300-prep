新手入門：什麼是 Power BI?

Power BI 是微軟的商業智慧（BI）工具：把散落在 Excel、資料庫、雲端服務裡的原始資料，整理成互動式的圖表報表，讓你和團隊「用資料回答問題」。它由三個部分組成：

元件是什麼你會用它做什麼
Power BI Desktop安裝在 Windows 的免費開發工具連接資料、清理轉換、建立模型與報表（考試的主戰場）
Power BI 服務（Service）雲端網站 app.powerbi.com發佈報表、排程更新、分享給同事、建儀表板
Power BI Mobile手機/平板 App隨時檢視報表與接收警示

① 準備資料（Prepare the data,25–30%）

這個領域考的是：把資料「接進來」和「洗乾淨」。對應工具是 Desktop 裡的 Power Query 編輯器（功能區「轉換資料」按鈕開啟）——你在裡面做的每一步轉換都會被記錄成「套用的步驟」，資料更新時自動重播，這就是它比手動改 Excel 強大的原因。

連接資料與儲存模式

按「取得資料」可連接數百種來源：Excel、CSV、SQL Server、SharePoint、網頁……連接時最重要的觀念是儲存模式——資料要「搬進來」還是「留在原地即時查」：

  • Import(匯入)：資料複製並壓縮進模型，查詢最快、功能最完整；需排程重新整理。預設模式，也是考題「效能最佳」的標準答案。
  • DirectQuery(直接查詢)：資料留在來源，每次互動都現查；適合近即時或超大資料，但視覺效果較慢、功能受限。
  • Dual(雙重)：視情境自動當 Import 或 DirectQuery 用，常用於複合模型中的維度表。
  • Live Connection(即時連線)：連到現成的語意模型直接重用模型與量值——「開發工作量最小」的選擇。
更新需求建議儲存模式
近即時（near real time）DirectQuery
每日/每週定期更新、追求視覺效能Import(或彙總表 Import)
維度表連接 DirectQuery 事實表Dual

Power Query 常考轉換

初學者最容易混淆的是「合併 vs 附加」與「Pivot vs Unpivot」，用場景記：

  • Merge(合併查詢)= 橫向 JOIN：兩張表靠共同鍵「加欄位」。例：訂單表 + 客戶表 → 每筆訂單多出客戶城市欄。
  • Append(附加查詢)= 縱向堆疊：相同欄位結構的表「加資料列」。例：一月銷售 + 二月銷售 → 一張總表。合併後記得停用原始查詢的載入以縮小模型。
  • Unpivot(取消樞紐)：欄名本身是資料（2022、2023、2024 三個年份欄）時，把它們轉成「年份/值」兩欄（寬轉長）。Pivot 相反。考題看到年份/月份當欄名，答案幾乎都是 Unpivot。
  • Group By(分組依據)：做彙總（每位客戶的訂單數、每月銷售額）。
  • Transpose(轉置)：整張表列欄互換，與 Pivot/Unpivot 是不同的東西。
  • Use first row as headers（第一列作標頭）、Fill Down/Up（向下/向上填滿，補合併儲存格造成的 null）、Split Column（分割欄）、Column From Examples（打幾個範例讓它自動推轉換）。

資料剖析：先看資料健不健康

Power Query「檢視」頁籤可開啟三個剖析工具，考試常考它們各自顯示什麼：

  • Column quality(資料行品質)：每欄的 Valid / Error / Empty 百分比——一眼看出哪欄有錯誤值。
  • Column distribution(資料行分佈):Distinct(相異值)與 Unique(唯一值)個數——判斷某欄可否當主鍵（每列都唯一）。
  • Column profile(資料行設定檔)：單欄的統計值（最小、最大、平均）與值分佈直方圖。
陷阱：剖析預設只看前 1,000 列，狀態列可切換成整個資料集。

處理錯誤

匯入時常見兩類錯誤訊息，考題會給你訊息問原因：

  • Dataformat.Error: We couldn't convert to Number——欄位裡混了無法轉數字的文字（如 "NA"）。解法：Replace Errors 換成預設值，或先 Replace Values 再轉型。
  • Expression.Error: The column 'X' wasn't found——來源欄位被改名或刪除，套用的步驟找不到它。
  • 選項對比：Replace Errors（把錯誤換成指定值，保留所有列）vs Remove Errors（整列刪除，列數會變少）vs Keep Errors（只留出錯的列，用來檢查）。

查詢摺疊（Query Folding）與效能

  • 轉換步驟若能翻譯回來源的原生 SQL 執行，叫「摺疊」——由資料庫做粗活，效率最好。在步驟上右鍵看 View Native Query：亮的代表可摺疊，灰的代表從該步起改由 Power BI 自己算。
  • 增量重新整理（只更新最新分割區）需要來源支援查詢摺疊。
  • 縮小模型的通則：刪掉用不到的欄與列、關閉「自動日期/時間」、避免高基數欄位（GUID、含秒的時間戳）、能彙總就先彙總。

② 模型化資料（Model the data,25–30%）

資料洗乾淨後，下一步是把多張表「接起來」成為模型，並用 DAX 定義計算。這是 Power BI 和 Excel 最不一樣、也是考試最重的部分。

星型結構（Star Schema）

建模的黃金法則：中間一張事實表（記錄發生的事：每筆訂單、每筆銷售，列數很多），周圍幾張維度表（描述人事時地物：客戶、產品、日期，列數少），維度表以「一對多」連向事實表，畫起來像星星：

關聯的三個設定

  • 基數：一對多（1:*）最常見；多對多盡量避免，用橋接表化解。
  • 交叉篩選方向：預設單向（維度 → 事實）。雙向（Both）會增加模稜兩可與效能風險，只在必要時用；要讓 RLS 沿雙向關聯傳遞需勾「Apply security filter in both directions」。
  • 作用中/非作用中：兩表間只能有一條實線（作用中）關聯。訂單日期、出貨日期都連日期表時，第二條是虛線，量值中用 USERELATIONSHIP() 暫時啟用。
日期表：要用時間智慧函數，需一張「每日一列、連續不斷」的日期表並「標示為日期資料表」。用 DAX 一行就能生：Date = CALENDAR(DATE(2020,1,1), DATE(2026,12,31))。

DAX 入門：計算資料行 vs 量值

DAX 是 Power BI 的公式語言，長得像 Excel 公式但操作整張表。第一課是分清兩種計算：

計算資料行（Calculated column）量值（Measure）
什麼時候算資料更新時逐列算好、存進模型使用者看圖時依當下篩選動態計算
計算情境列內容（row context）：一次看一列篩選內容（filter context）：看被篩出的一群列
佔空間？佔記憶體不佔（只存公式）
用途要放進交叉分析篩選器/座標軸的欄位彙總數字、KPI——考題問「最小化模型大小」時選它

白話比喻：計算資料行像在 Excel 表格右邊多拉一欄公式；量值像樞紐分析表裡的「加總欄位」，換個篩選數字就跟著變。

迭代函數（SUMX）：逐列算再加總

SUM 只能加「一個現成的欄位」；如果金額要用數量 × 單價現算，就要用 SUMX 逐列迭代：

營收 = SUMX ( Sales, Sales[Qty] * Sales[單價] )

它逐列計算：1×30000 + 2×500 + 1×500 + 3×900 + 1×28000 = 62,200。X 結尾的函數（SUMX/AVERAGEX/COUNTX/MAXX）都是這個「一列一列算，最後彙總」的模式。

CALCULATE：改寫篩選再計算

先懂篩選內容（filter context）：量值的結果永遠取決於「當下被篩掉剩哪些列」。你點了交叉分析篩選器的「周邊」，營收 就只加 S2、S3、S4 = 3,700。CALCULATE 的作用是用你指定的條件覆寫這個篩選:

周邊營收 = CALCULATE ( [營收], Products[Category] = "周邊" )      -- 強制只算周邊
總營收   = CALCULATE ( [營收], ALL ( Products ) )                 -- 拿掉 Products 的所有篩選
占比     = DIVIDE ( [營收], CALCULATE ( [營收], ALL ( Products ) ) )

「占比」是最經典的組合：分子隨使用者篩選變動，分母被 ALL 固定成整體——在「周邊」列上會得到 3700 / 62200 = 5.9%。若希望分母只算「使用者選取範圍的總和」則改用 ALLSELECTED()。

跨表取值：RELATED、RELATEDTABLE、LOOKUPVALUE

口訣：站在哪張表，決定用哪個函數。

1. RELATED——站在「多」端（Sales），去「一」端拿一個值。在 Sales 加計算資料行 品名 = RELATED ( Products[Name] )，每列沿著關聯把自己的產品名帶回來：

3. LOOKUPVALUE——兩張表根本沒建關聯時的查表。像 Excel 的 VLOOKUP:品名 = LOOKUPVALUE ( Products[Name], Products[ID], Sales[PID] )，意思是「去 Products 找 ID 等於我這列 PID 的那一列，回傳它的 Name」。有關聯時用 RELATED 效能較好，LOOKUPVALUE 留給無關聯的場合。

你站在想拿用
多端（事實表）一端的單一值RELATED
一端（維度表）多端的整批列（再彙總）RELATEDTABLE + COUNTROWS/SUMX
任何表無關聯表的值LOOKUPVALUE

其他必考主題

  • 時間智慧:TOTALYTD（年初至今）、SAMEPERIODLASTYEAR（去年同期）、DATESINPERIOD（近 N 個月滾動）、DATEADD（平移）。前提：連續且「標示為日期資料表」的日期表。
  • 計數家族:COUNT（數值）/COUNTA（非空白）/COUNTROWS（列數）/DISTINCTCOUNT（相異值）——上面 Sales 表的 DISTINCTCOUNT(Sales[PID]) = 3。
  • VAR … RETURN：把重複的算式存進變數，只算一次又好讀。
Sales YTD = TOTALYTD ( [營收], 'Date'[Date] )
Sales LY  = CALCULATE ( [營收], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
Rolling12 = CALCULATE ( [營收],
              DATESINPERIOD ( 'Date'[Date], MAX ( 'Date'[Date] ), -12, MONTH ) )

資料列層級安全性（RLS）

讓不同人看同一份報表卻只看到自己的資料。三步驟：

  1. Desktop：「模型化 → 管理角色」建角色，寫資料表篩選 DAX，如 [Region] = "West"；要「每人看自己的」就用動態式 [Email] = USERPRINCIPALNAME()。
  2. Desktop：「檢視身分（View as）」模擬測試。
  3. 發佈後在服務中打開語意模型的「安全性」頁面，把使用者/群組指派進角色。
最常考：RLS 只對 Viewer 角色生效——工作區的 Admin/Member/Contributor 一律看得到全部資料。

效能最佳化

  • Performance Analyzer（檢視頁籤）：錄下每個視覺效果花多少毫秒、DAX 查詢多久，可匯出 JSON 慢慢分析。
  • 降低欄位基數（拆掉時間的秒、date 與 time 分兩欄）、整數當索引鍵、量值取代計算資料行、大表做彙總表。

③ 視覺化與分析資料（Visualize and analyze the data,25–30%）

模型好了就能拉報表。考試重點不是美感，而是「什麼需求配什麼視覺效果」與互動功能的正確名稱。

互動、篩選與導覽

  • 篩選層級：視覺效果 → 頁面 → 所有頁面。交叉分析篩選器（Slicer）是放在畫布上給使用者點的篩選；「同步交叉分析篩選器」讓它跨頁生效。
  • 編輯互動（Edit interactions）：控制點 A 圖時 B 圖要被篩選、被醒目提示、還是不受影響。
  • 鑽研（Drill through）：摘要頁右鍵某筆資料 → 帶著篩選跳到明細頁。目標頁要設定鑽研欄位。
  • 書籤（Bookmark）+ 按鈕 + 選取窗格：存住頁面狀態做導覽選單、「重設篩選」鈕、顯示/隱藏切換。
  • 條件式格式設定：依量值上色、資料橫條、圖示；「依欄位值」可直接用存色碼的欄位。
  • Top N 篩選、群組/量化（Groups/Bins）、行動版直向配置。
  • 分析窗格：平均/中位數/百分位線、趨勢線；折線圖的預測（Forecast）與異常偵測（Anomaly detection）。

儀表板 vs 報表（常考差異）

  • 儀表板只存在雲端服務，由報表視覺效果「釘選」而成；跨多份報表的重點可以釘在同一板。
  • 資料警示只能設在儀表板的卡片、KPI、量測計磚上；要通知別人得串 Power Automate。
  • 訂閱定期寄快照；註解可 @ 提及使用者（含外部使用者）。

④ 管理與保護 Power BI(Manage and secure,15–20%)

報表做好後要放上雲端給別人用，這個領域全部圍繞四個問題：誰能做什麼？資料怎麼保持最新？怎麼分享出去？怎麼不外洩？把雲端服務想像成公司的共用雲端硬碟，概念就都好懂了。

工作區與四種角色

工作區就是雲端上的「共用資料夾」，裡面放語意模型、報表、儀表板。給每個成員指派一種角色，權限由大到小：

角色比喻關鍵權限
Admin資料夾擁有者什麼都能做，包含刪除工作區、管理所有成員、更新/刪除 App
Member資深協作者發佈與更新 App、加入權限較低的成員、共用內容
Contributor一般編輯者建立/修改/刪除內容、排程更新；但不能分享給別人、不能發佈 App
Viewer訪客只能看和互動；唯一會套用 RLS 的角色
記憶關鍵：Member 與 Contributor 的分水嶺是「能不能分享/發佈 App」；Viewer 與其他三者的分水嶺是「RLS 只對 Viewer 生效」。

資料更新與閘道：雲端怎麼拿到公司內部的資料？

發佈到雲端後，報表要定期回來源抓新資料。問題是：雲端服務碰不到你公司內網的資料庫——這就是閘道存在的原因：

  • 閘道標準模式：裝一次、多人多來源共用（企業正解）；Personal mode 只限個人使用。
  • 排程更新次數上限：共用容量 8 次/天,Premium 48 次/天。
  • 語意模型兩個月沒人使用會被「因閒置停用排程」——任何人再打開相關報表就自動恢復，不用重設。
  • 增量重新整理：用 RangeStart/RangeEnd 參數把大表切分割區，每次只更新最新的部分；需要來源支援查詢摺疊。
  • OneDrive/SharePoint 上的 .pbix 檔約每小時自動同步一次，不吃排程額度。

從開發到上線：部署管線與範本

  • 部署管線（Deployment pipelines）：像軟體的「開發 → 測試 → 生產」三個環境，一鍵把內容往下一階段搬，並可設定規則讓測試環境自動改連測試資料庫；需 Premium/Fabric 容量。
  • .pbit 範本：把做好的東西「去掉資料」存成範本發給同事——對方開啟時輸入自己的參數，重用你的整套查詢與報表，又不會看到你的資料。
  • 使用量計量報告（Usage metrics）：看每份報表誰在看、看了幾次，決定哪些該維護哪些該下架。
